# Frontend and graphics harness

- Build a coherent runnable vertical slice early, then iterate with browser evidence. Source inspection alone cannot verify rendering, interaction, responsive layout, ES Modules, WebGL, GLSL compilation, audio controls, persistence, or error recovery.
- Keep disposable probes, alternate pages, generated browser profiles, and one-off diagnostic scripts under `.lunascope/scratch/`; never scatter `diag*.html`, `mini.js`, browser profiles, or similar investigation residue through the deliverable. Prefer the built-in browser report over custom harnesses.
- Use `check_browser_page` during implementation as well as final verification. It serves the workspace over a temporary loopback HTTP server, drives bounded selectors/keys, captures the final DOM and screenshot, records console/runtime errors and shader compile/link diagnostics, and reports WebGL context state, responsive overlay coverage, luminance percentiles, dynamic range, dark/highlight ratios, clipping, and blank-canvas signals. For a hard simulation bug, expose a small JSON-safe `window.__lunascopeDiagnostics`, `<meta name="*-verify">`, or `[data-lunascope-signal]` value so the same report can observe domain state without an ad-hoc page.
- For a visual task, request a screenshot and inspect the returned image when the selected model supports vision. Use the screenshot together with runtime evidence; neither one replaces the other. When vision is unavailable, use the measured visual-quality signals as an engineering instrument: for a dark cinematic scene, require meaningful dark and highlight ranges without broad clipping; for a fullscreen mobile experience, do not let a fixed HUD dominate the viewport. A signal is evidence to investigate against the brief, not a universal aesthetic rule.
- Test the actual entry page at desktop and mobile viewports. Exercise named controls and keyboard paths through actions. For WebGL work, require a visible canvas, a live non-lost WebGL context, no shader/runtime errors, and a non-empty screenshot.
- Never substitute a black sphere, flat ring, static texture, video, screenshot, or placeholder effect when the user requires a shader, simulation, ray tracer, particle system, or other procedural implementation. Inspect the shader source and runtime evidence that distinguishes the required mechanism from a visual fake.
- Keep external runtime dependencies local and offline-capable. Do not use a CDN. Vendor the exact upstream asset and its license rather than recreating the library.
- Treat quality tiers, mobile/Retina behavior, state persistence, context-loss recovery, URL automation, debug modes, parameter counts, presets, and shortcuts as testable product behavior, not documentation claims.
- When a browser check fails, use the console/runtime report and screenshot to repair the smallest concrete defect, then rerun the same check. Do not downgrade the criterion merely because the first attempt failed.
- If the same measured blocker survives several focused repairs and a downstream writable Reviewer is assigned, preserve the current coherent implementation and exact failing evidence for that Reviewer. Do not restart the project or keep broadening ad-hoc diagnostics inside one degraded context.
